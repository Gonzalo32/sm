# CP33.5 — INDEPENDENT HISTORICAL VALIDATION DATA ACQUISITION AUDIT

## 1. OBJECTIVE & SCOPE

This checkpoint conducts a forensic audit to determine how the project can obtain a sufficiently deep, reproducible, independent historical market dataset for formal Out-Of-Sample (OOS) validation of the TradeSea ICT system.

This audit follows the CP33 series:
* **CP33.3.x:** TradeSea Runtime Historical Capability Audit
* **CP33.3.y:** Runtime Historical Accumulation & Persistence Audit
* **CP33.3.z:** Runtime Data Lifecycle & Integrity Audit
* **CP33.4:** Runtime Historical Acquisition Strategy Audit

CP33.4 established that the TradeSea runtime delivers an initial window of approximately **31 bars per timeframe series**, from which local runtime accumulation (`CandleStore.ts`) progressively builds an operational dataset over elapsed time. However, operational runtime accumulation **CANNOT** serve as controlled OOS validation evidence:

$$\text{TradeSea Runtime Historical Store} \neq \text{OOS Validation Dataset}$$

The explicit objective of CP33.5 is to research, evaluate, and define independent data acquisition paths to supply reproducible NQ/MNQ historical OHLCV data without relying on an external market-data provider integrated inside the TradeSea engine or runtime.

## 4. SOURCE CATEGORIES INVESTIGATED

### Category A — Public / Free Historical Datasets
- **Scope:** Public GitHub repositories, Kaggle financial datasets, academic repositories, CME public daily samples.
- **Audit Findings:** Publicly uploaded NQ/MNQ CSVs frequently lack provenance verification, omit roll adjustment details, contain unverified timezone offsets, or are truncated.
- **Licensing & Integrity:** Unclear licensing; risk of undocumented synthetic gap filling or missing ETH session bars.
- **Classification:** `NOT_VIABLE` for primary formal OOS validation.

### Category B — Commercial Market-Data APIs
- **Databento (`GLBX.MDP3`):** Direct CME Globex MDP 3.0 venue data capture. Supports `ohlcv-1m` schema for NQ/MNQ, continuous roll types (`NQ.c.0` calendar, `NQ.v.0` volume), multi-year history (NQ back to 2010, MNQ back to 2019), UTC timestamps (`ts_event`), pay-as-you-go pricing, client SDKs (Python/Rust/C++).
- **CME DataMine:** Official CME Group historical archive. Direct exchange-certified data for NQ/MNQ (tick, 1m, daily). Immutable, AWS S3 delivery, official CME licensing, pay-per-dataset or subscription.
- **dxFeed:** Financial data vendor supporting CME futures historical 1m bars and tick replay via REST / WebSocket / CSV bulk extractions. Custom quote pricing.
- **Barchart OnDemand:** Futures API providing intraday historical bars. Custom API subscription required for futures intraday history.
- **Polygon.io:** Explicitly **does NOT** provide historical intraday bars for CME futures (NQ/MNQ).
- **Classification:** `VIABLE_FOR_FURTHER_INVESTIGATION` (Databento, CME DataMine, dxFeed); `NOT_VIABLE` (Polygon.io).

### Category C — Existing Platform Exports
- **TradingView Export:** Requires Pro+/Premium plan. Strictly limited to visible chart bars (max 10,000 to 20,000 candles). Licensing strictly restricts non-commercial personal UI use; explicitly prohibits building external validation databases.
- **Rithmic / Sierra Chart / NinjaTrader Exports:** Platform CSV export capabilities permit extracting historical intraday bars from connected broker feeds (e.g. Rithmic, CQG). Requires active broker account and exchange data subscription.
- **Classification:** `PARTIAL` (NinjaTrader/Sierra Chart exports with verified broker feed); `NOT_VIABLE` (TradingView export due to bar limits & licensing terms).

### Category D — User-Owned Historical Archives
- **Scope:** Pre-existing local CSV/JSON files in project storage.
- **Requirements:** Must pass strict audit for provenance, contract specification, UTC timestamps, session boundaries, and SHA-256 hash manifest before being considered for validation.
- **Classification:** `PARTIAL` pending forensic provenance audit.

## 6. CONTRACT / SYMBOL NORMALIZATION

Futures contracts expire quarterly (March `H`, June `M`, September `U`, December `Z`). A formal OOS dataset must distinguish contract representations:

```text
NQ Contract Types:
├── Front-Month Contract:   e.g., NQZ26 (Dec 2026 contract only)
├── Continuous (Calendar):  e.g., NQ.c.0 (Rolls on contract expiration date)
└── Continuous (Volume):    e.g., NQ.v.0 (Rolls when new contract volume exceeds front month)
```

$$\text{NQ Specific Contract (NQZ26)} \neq \text{NQ Continuous Unadjusted} \neq \text{NQ Continuous Back-Adjusted}$$

### Specification:
- **Canonical Symbol Naming:** `NQ` (E-mini Nasdaq-100), `MNQ` (Micro E-mini Nasdaq-100).
- **Primary Contract Mode for ICT:** **Continuous Unadjusted (Volume Roll)**. ICT structural levels (FVG, Order Blocks, Liquidity Swings) rely on absolute price levels during live sessions; price-offset back-adjustment alters historical high/low values and distorts FVG gap sizes.

---

## 7. CONTRACT ROLLOVER ANALYSIS

```text
ROLLOVER_POLICY = UNADJUSTED_VOLUME_ROLL
```

1. **Roll Event Condition:** Contract roll occurs when the volume of the active secondary quarterly contract exceeds the primary front-month contract (typically 6–8 days prior to expiration).
2. **Price Adjustment:** **UNADJUSTED**. Historical bars prior to the roll retain their native exchange-traded OHLC values. No synthetic price offset shift (back-adjustment) is applied.
3. **Gap Handling:** Rollover price gaps between expiring and new front-month contracts are preserved as true market price differentials and marked with a `rollover_event` metadata tag in dataset manifests.

## 8. TIMESTAMP & TIMEZONE AUDIT

### Semantics Standard:
- **Timezone Standard:** `UTC` (Coordinated Universal Time). All local exchange times (e.g. CME Chicago CT, New York ET) are normalized to UTC upon ingestion.
- **Bar Timestamp Convention:** `Start-of-Bar` (e.g., a 5m bar spanning 09:30:00 to 09:34:59 UTC has timestamp `09:30:00.000Z`).
- **ISO-8601 Format:** `YYYY-MM-DDTHH:mm:ss.sssZ` (e.g. `2026-03-15T13:30:00.000Z`).
- **Daylight Saving Time (DST):** UTC normalization eliminates ambiguities caused by Eastern Time (EDT/EST) transitions.

## 9. SESSION DEFINITION

```text
SESSION_SCOPE = FULL_GLOBEX_ETH_RTH
```

1. **Full Futures Session (Globex):** CME E-mini futures trade 23 hours/day from 18:00 ET (Sunday) to 17:00 ET (Friday) with a daily maintenance break from 17:00 ET to 18:00 ET.
2. **Session Sub-types:**
   - **RTH (Regular Trading Hours):** 09:30 ET to 16:00 ET.
   - **ETH (Extended Trading Hours):** 18:00 ET (previous day) to 09:30 ET.
3. **ICT Engine Requirement:** ICT liquidity sweep and Midnight Open / Asian Range / London Session analysis **require** full Globex ETH + RTH session coverage. RTH-only datasets are insufficient for complete ICT model validation.

## 10. OHLCV SEMANTICS & DERIVED-TIMEFRAME POLICY

```text
DERIVED_TIMEFRAME_POLICY = OPTION_B_DERIVED_FROM_1M
```

### Timeframe Policy Comparison:

| Option | Description | Tradeoffs & Recommendation |
| :--- | :--- | :--- |
| **Option A (Native Provider 5m/15m/1H)** | Fetch each timeframe directly from provider API. | Higher API request count; potential minor aggregation discrepancies across endpoints. |
| **Option B (Derived from 1m Bars)** | **RECOMMENDED.** Ingest base `1m` OHLCV; deterministically aggregate `5m`, `15m`, `1H` bars. | **100% deterministic & mathematical alignment.** Ensures Open of first 1m bar = Open of 5m bar, High = max(1m Highs), Low = min(1m Lows), Close of last 1m bar = Close of 5m bar, Volume = sum(1m Volume). |
| **Option C (Derived from 5m Bars)** | Ingest `5m` bars and aggregate to higher timeframes. | Cannot reconstruct `1m` timeframe; limits granular structural break analysis. |
